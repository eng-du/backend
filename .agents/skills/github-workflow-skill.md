# 안티그래비티 깃허브 워크플로우 스킬 (GitHub Workflow Skill)

## 0. 필수 선행 절차 (반드시 지켜라)
실제 실행(터미널 명령어, MCP 도구 호출)에 앞서 반드시 다음 순서를 따른다.

1. **실행 계획을 아티팩트로 작성한다.**
   - 커밋할 파일 목록과 커밋 메시지
   - 이슈 제목 및 내용
   - PR 제목과 본문 초안
2. **사용자 리뷰 및 승인을 기다린다.**
3. **승인 후에만 실제 작업을 실행한다.**

## 1. 사전 확인
- **브랜치 네이밍 규칙**: `[타입]/#[이슈번호]-[기능-요약]`
  - 타입: 소문자 (feat, fix, refactor, chore, test, style)
  - 기능 요약: 케밥 케이스
  - 예시: `feat/#139-run-and-learn-submit`
- 현재 브랜치가 `dev`이거나 규칙에 맞지 않으면 새 브랜치 생성을 제안한다.
- PR 본문 작성을 위해 `.github/pull_request_template.md` 파일을 반드시 읽는다.

## 2. 이슈 생성
- **반드시 GitHub MCP 도구**(`issue_write`)를 사용한다. 터미널 명령어 사용 금지.
- 이슈 생성 후 발급된 번호를 브랜치명과 PR에 반영한다.

## 3. 커밋
- **반드시 커밋을 진행하기 전에 전체 테스트 코드(예: `./gradlew test`)를 실행하고 모두 성공하는지 확인해야 한다.** (실패 시 원인을 수정 후 커밋한다)
- 환경 파일, 설정 파일은 사용자 요청 없이 커밋하지 않는다.
- **커밋 분할(쪼개기) 규칙**:
  - 변경 사항이 많은 경우 기능 단위, 도메인 단위 등 **논리적인 단위**로 잘게 쪼개서 커밋한다 (예: User 도메인 확장 1개, 전략 패턴 전환 1개).
  - **주의 사항**: 같은 이슈 내에서 'A를 구현'하고 나중에 'A에서 발생한 버그 수정 및 리팩토링'을 했다면, 이를 분리해서 지저분하게 커밋하지 마라. 해당 이슈의 최종 결과물 관점에서 **수정된 내역을 기존 기능 커밋에 합쳐서(깔끔한 하나의 변경사항으로)** 커밋해야 한다. 작업 과정(시행착오)을 나열하는 커밋을 만들지 마라.
- **커밋 타입**:
  - `feat`: 새로운 기능 구현
  - `fix`: 버그 수정 및 예외 처리
  - `refactor`: 기능 변경 없이 내부 구조 개선
  - `chore`: 빌드, 환경 설정, DDL 등 비즈니스 로직 외 작업
  - `test`: 테스트 코드 추가 및 수정
  - `style`: 코드 형식 수정, 불필요한 코드/주석 제거
- **코드 리뷰 반영 커밋 포맷**: `[타입]: [리뷰반영] 커밋 내용`

## 4. PR 생성
- **반드시 GitHub MCP 도구**(`create_pull_request`)를 사용한다. 터미널 명령어 사용 금지.
- **대상 저장소**: `eng-du/backend` (개인 레포 `young999999999/eng-du-be` 아님)
- **Base 브랜치**: `dev`
- **PR 제목**: `[FEAT or FIX or REFACTOR or CHORE] 내용 요약` (대문자)
- **PR 본문 작성 규칙**:
  - `pull_request_template.md` 양식을 따른다.
  - 결과 중심으로 작성한다.
  - 서술형 단정문으로 작성한다. 리뷰어에게 요청·부탁하는 표현은 사용하지 않는다.
